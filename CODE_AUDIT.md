# Аудит проекта автопарсинга реестров MAVIS

Дата аудита: 31.07.2026

## 1. Итоговый вывод

Для этого проекта правильная схема — не проверять белорусские сайты в момент каждого пользовательского запроса, а один раз в неделю собирать полные снимки реестров на рабочем Mac, проверять качество данных и публиковать только валидные JSON. Приложение после этого выполняет моментальный поиск по готовым снимкам.

Исходный архив нельзя считать готовым к эксплуатации: часть баз пустая или неверно распознана, облачный GitHub Actions продолжал публиковать результат даже после ошибки парсера, а шесть из восьми реестров в интерфейсе фактически зависели от Chrome-расширения, кода которого в архиве нет.

## 2. Что было в исходном проекте

- Одностраничное статическое приложение `index.html` без серверной части.
- Развёртывание предполагалось через GitHub и Render.
- Набор Python-парсеров и JSON-файлов в `data/`.
- GitHub Actions с ежедневным запуском парсеров в облаке.
- Интерфейс обмена с Chrome-расширением через сообщения `MAVIS_EXT`.
- Само расширение, его `manifest.json`, background/content scripts и селекторы в архив не вошли.

## 3. Критические проблемы исходной версии

### 3.1. Публикация повреждённых данных

Workflow разрешал продолжить выполнение после ошибки парсера. Некоторые парсеры успевали записать пустой JSON, после чего GitHub Actions всё равно коммитил его. В результате временная недоступность источника превращалась для пользователей в ложное «не найдено».

### 3.2. Неверная структура старых снимков

Проверка исходных JSON показала:

- `spk.json` — 1 техническая запись вместо реестра;
- `att.json` — более 3 000 строк, но организация, адрес и номер документа сдвинуты по колонкам;
- `attoff.json` — пустой снимок;
- `iso.json` — пустой снимок;
- `spk2.json` — часть записей без организации и служебный заголовок в номере документа;
- `osp.json` — единственный снимок, прошедший базовую проверку качества;
- `metal.json`, `lic.json`, `spec.json` — отсутствовали.

Повреждённые старые снимки убраны из рабочей папки `data/`, чтобы приложение не выдавало ложные результаты.

### 3.3. Архитектура зависела от отсутствующего расширения

Веб-интерфейс умел отправлять расширению команды поиска и обновления базы, но кода расширения в архиве нет. Поэтому восстановить точные сетевые запросы, селекторы и обработку CAPTCHA только по этому ZIP невозможно.

### 3.4. Несоответствие ТЗ по хранению

Режим реестров сохранял историю поисков и картотеку компаний в `localStorage`. Это удалено. Теперь результаты проверки существуют только на экране текущей вкладки; сохраняются лишь настройки выбранного профиля реестров.

### 3.5. Риск безопасности Bitrix24

В клиентском `index.html` находится входящий webhook Bitrix24. Любой секрет внутри браузерного JavaScript нельзя считать защищённым. Его необходимо отозвать/перевыпустить и в отдельной задаче перенести Bitrix-запросы в серверный endpoint. В этой итерации webhook не удалён, чтобы не сломать существующий генератор КП.

## 4. Что сделано в версии local-weekly-v1

- Добавлен единый локальный оркестратор `scripts/run_weekly.py`.
- Перед обновлением создаётся резервная копия последней базы.
- Каждый новый снимок проверяется по количеству записей, структуре и качеству ключевых полей.
- Пустой, резко уменьшившийся или неверно распознанный результат не заменяет рабочую базу.
- Добавлен общий статус обновления `data/registry_status.json`.
- Добавлена публикация через обычные `git commit` и `git push` с локального Mac.
- Добавлена установка еженедельного задания macOS через `launchd`: каждый понедельник в 06:00.
- Автозапуск использует `.venv/bin/python`, где установлены зависимости проекта.
- GitHub Actions больше не парсит реестры; он только валидирует изменённые JSON.
- Интерфейс переведён на параллельную загрузку готовых снимков и моментальный поиск без расширения.
- JSON реестров исключены из service-worker cache, поэтому браузер получает свежий опубликованный файл.
- Удалено сохранение истории проверок и картотеки компаний.
- Добавлены самотесты парсеров и синтетические HTML-примеры.
- Добавлен диагностический Playwright-сборщик для JS-реестров: HTML, скриншоты и сетевые ответы.

## 5. Статус коннекторов

| Источник | Статус кода | Что нужно перед рабочим запуском |
|---|---|---|
| СПК старый | базовый парсер переписан | проверить на Mac по живому сайту и при необходимости уточнить пагинацию |
| СПК новый | базовый парсер переписан | проверить поля организации и номера на живом сайте |
| Аттестаты действующие | базовый парсер переписан | проверить реальные заголовки и виды работ |
| Аттестаты отменённые | защита от пустой перезаписи добавлена | проверить реальные колонки и основания прекращения |
| ISO / СУОТ | старый API-подбор сохранён, пустая перезапись запрещена | снять сетевой ответ через Playwright и закрепить фактический API |
| Сертификаты на металл | коннектора нет | снять сетевой ответ и написать нормализатор |
| ОСП | снимок и парсер проходят базовую проверку | подтвердить актуальную структуру на Mac |
| Лицензии МВД/МЧС/Госпромнадзор | коннектора нет | определить поиск/выгрузку через браузер и написать нормализатор |
| Аттестаты специалистов | старый парсер сохранён | проверить на живом сайте; это дополнительный девятый источник |

## 6. Что проверено технически

- Все Python-файлы компилируются без синтаксических ошибок.
- Синтетические тесты парсеров СПК, СПК нового и аттестатов проходят.
- Shell-скрипт установки launchd проходит синтаксическую проверку.
- JSX основного приложения проходит синтаксический разбор TypeScript.
- Валидатор правильно блокирует старые повреждённые снимки и принимает ОСП.
- Проверен сценарий ошибки источника: старый рабочий JSON сохраняется и не перезаписывается пустым результатом.

## 7. Ограничение текущего аудита

Из этой среды нельзя подтвердить рабочую загрузку всех белорусских реестров от начала до конца: часть сайтов блокирует внешние запросы, а код ранее использовавшегося Chrome-расширения отсутствует. Поэтому версия является безопасным рабочим каркасом и первой доработанной итерацией, но три сложных коннектора — ISO, металл и лицензии — нельзя честно назвать завершёнными до одного диагностического запуска на вашем Mac.

## 8. Следующий технический шаг

На Mac выполнить:

```bash
cd /путь/к/проекту
source .venv/bin/activate
python3 scripts/capture_browser.py --sources iso metal lic --wait 45
```

После этого в `snapshots/` появятся сетевые JSON и HTML. По ним фиксируются реальные endpoint и схема полей, после чего три коннектора добавляются в `registry_sources.json` и включаются в еженедельный оркестратор.
